HOST
0 CLI / IDE reads devcontainer.json — resolves localEnv & variables
host process

What happens

The CLI (devcontainer up) or VS Code Remote-Containers extension reads and parses devcontainer.json on the host, before any container exists.

This is where the config structure is validated and feature ordering resolved. ${localEnv:VAR} references are not all substituted here — only those in build.args are resolved at this stage (before the image build). Values in containerEnv, remoteEnv, and mounts carry their ${localEnv:X} syntax through to later phases.

"The host" throughout the lifecycle always means whoever is running devcontainer up — not whoever built or published the image.

⚠ which localEnv is whose? Only build.args resolves ${localEnv:X} from the image builder's host — and gets baked into image layers. Every other property (containerEnv, mounts, remoteEnv) resolves ${localEnv:X} at runtime from the current user's host. This means a distributed image is safe to ship with containerEnv or mounts referencing localEnv — each user gets their own values, not the image author's.

2b Feature install.sh runs — one Docker layer per feature
root

What happens

Each feature's install.sh runs as a RUN layer inside a docker build operation — this is build time, not runtime. The CLI generates a synthetic Dockerfile that layers all features on top of your base.

The spec mandates that install.sh always runs as root — this is not a default that can be overridden. The rationale is that root is required to install packages and modify system paths, and because sudo may not exist in minimal base images. To perform work as the non-root user, the script should su ${_REMOTE_USER} -c "..." explicitly for those portions.

A key pattern: install.sh can write scripts into the image (e.g. to /usr/local/share/) and then reference them in the feature's postCreateCommand or onCreateCommand metadata. This is how features bridge build-time setup with runtime execution. The connection between the installed path and the lifecycle hook command is entirely the feature author's responsibility — there is no spec enforcement that the script exists at the path named in the command.

This is why feature installs survive container restarts — they are baked into the image.

Environment available to install.sh

_CONTAINER_USERvalue of containerUser (or _REMOTE_USER fallback)

2c Final image committed — feature metadata merged into runtime config
docker

What happens

The CLI writes accumulated feature runtime metadata into the final image as a Docker LABEL named devcontainer.metadata. The value is a JSON array — one entry per feature plus one for the base config — containing properties like containerEnv, mounts, entrypoint, postCreateCommand, and other runtime contributions from each feature.

This label is the storage mechanism for the merged config. It travels with the image, making the image self-contained — a prebuilt image distributed via a registry carries its own runtime requirements with it.

The merge itself does not happen here. The CLI writes an array and intentionally defers merging. At step 3, when docker run is called, the CLI reads this label back out of the image, merges it with the local devcontainer.json using property-specific rules, and uses the combined result to construct the docker run command.

Outputs written to image

cache labelcontent-addressable hash label so the CLI can detect whether a rebuild is needed on next devcontainer up

RUNTIME — container start
3 docker run — container created and started
docker daemon

What happens

Before issuing docker run, the CLI reads the devcontainer.metadata label from the image, merges it with the local devcontainer.json using property-specific rules (arrays are concatenated; scalars prefer devcontainer.json), and constructs the final docker run arguments from the combined config.

Docker then creates and starts the container. Mounts are attached, ports forwarded, and the init process launches. containerEnv values — from the merged config — are passed as --env flags and injected for all processes in the container.

remoteEnv values are applied later — only to the VS Code server and its child processes (terminals, tasks, extensions).

Variables injected at docker run

containerEnvset for ALL container processes; ${localEnv:X} resolved HERE from the runner's host — not the image builder's
mounts${localEnv:X} and ${localWorkspaceFolder} substituted here at docker run time — e.g. source=${localEnv:HOME}/.ssh works directly without forwarding
forwardPortsport mapping passed to docker
runArgsraw args appended to docker run — e.g. --cap-add, --network
remoteEnvNOT yet injected — VS Code server only

4 onCreateCommand — runs once, ever, on first container creation
root (default) or merged remoteUser if set

What happens

Runs once when the container is created from the image for the first time. Does not re-run on docker start or container rebuild unless the image changes.

Executed inside the running container via docker exec. Shell is /bin/sh -c for strings; object form runs each command in parallel.

Useful for one-time heavy setup that you want cached (e.g. bundle install if gems are baked into the image).

localEnv✗ — host only, unless forwarded via containerEnv

5 updateContentCommand — re-runs when image or workspace content changes
root (default) or merged remoteUser if set

What happens

Like onCreateCommand but runs again whenever the devcontainer detects content changes (new image build, or workspace folder change when using a volume clone).

In practice: use this for dependency installs that should re-run when your lockfile changes — e.g. bundle install, yarn install.

Same execution model as onCreateCommand — docker exec into running container.

remoteEnv✗ not yet
localEnv✗ unless forwarded

6 postCreateCommand — runs once after container creation is complete
remoteUser ← default or root if no remoteUser set

What happens

The most commonly used lifecycle hook. Runs once when the container is first created, after onCreateCommand and updateContentCommand complete.

Runs as remoteUser if set — this is the key difference from earlier hooks. If remoteUser is not set, falls back to containerUser, which itself defaults to the image's USER or root.

The workspace folder is mounted and accessible. This is where you'd run git config, set up dotfiles, install user-level tools.

Environment available

containerEnv✓ available
remoteEnv✗ VS Code server still not running
localEnv✗ unless forwarded via containerEnv
USERremoteUser value — typically your non-root dev user
HOMEhome dir of remoteUser
WORKDIRworkspaceFolder (e.g. /workspaces/myapp)
⚠ postCreateCommand user trap postCreateCommand runs as remoteUser — but not with a full login shell. This means .bashrc / .profile are not sourced. If your script depends on PATH additions from those files (e.g. rbenv, nvm shims), you must either source them explicitly or use absolute paths.

What happens

Runs every time the container starts (create or restart). This is the only lifecycle hook that runs on restart.

Because it runs via the VS Code server, it does have access to remoteEnv — unlike the earlier hooks.

Good for: starting background services, writing runtime config files, port-forwarding helpers.

containerEnv vs remoteEnv
The most confusing distinction in the spec. Here's the mechanical difference.
containerEnv Set via --env on docker run. Visible to ALL processes in the container — init, cron, background daemons, everything. Set once at container creation; to change it you must recreate the container. ${localEnv:VAR} references are resolved at docker run time from the runner's host — not the image builder's.
remoteEnv Injected by the VS Code server process into itself and its children only. Background processes not spawned by VS Code do not see these. Can reference ${containerEnv:VAR} and ${localEnv:VAR}. Changes take effect on container restart without image rebuild. Use for dev-specific vars (tokens, editor config).
⚠ getting localEnv into lifecycle scripts Lifecycle scripts (postCreateCommand etc.) do not get ${localEnv:X} substitution directly. To pass a host variable in, add it to containerEnv — it will be injected as a real environment variable at docker run time and will then be present in all scripts. Never hardcode secret values — use localEnv references so the value stays on the host.

Mounts: ${localEnv:X} in a mount's source= is resolved directly at docker run time with no forwarding needed. e.g. "source=${localEnv:HOME}/.ssh,target=/home/vscode/.ssh,type=bind" works as-is.
✓ distributing images safely Because containerEnv, remoteEnv, and mounts all resolve ${localEnv:X} from the runner's host at container creation time, these are safe to ship in a published devcontainer.json alongside a pre-built image. Each user gets their own environment's values — ${localEnv:HOME} points to their home directory, ${localEnv:MY_TOKEN} reads their token. The only property that captures the builder's environment and bakes it into the image is build.args — avoid putting user-specific or sensitive values there.
User Resolution Rules
Three distinct user concepts — and how conflicts between feature and devcontainer.json values are resolved.
Property Controls Merge rule Default if unset
remoteUser User for all lifecycle hooks (onCreateCommand, updateContentCommand, postCreateCommand, postStartCommand, postAttachCommand) and all tool/terminal sessions. There is one resolved value for the whole container — all hooks use it. Last value wins. Priority order: devcontainer.json > Features > image label. Your devcontainer.json always wins over any feature. Falls back to containerUser → image USER → root
containerUser Default identity for all container processes not otherwise overridden. Used as the fallback when remoteUser is not set. Last value wins (same order) Image USER instruction or root
Feature _REMOTE_USER The resolved remoteUser value passed as an env var to feature install.sh at build time, so features can configure the right account (chown dirs, add to groups). Reflects the winner of the merge above. Read-only — derived from resolved remoteUser Same as _CONTAINER_USER if remoteUser unset
runArgs: ["-u", "…"] Overrides the docker run user at the OS level — bypasses containerUser and remoteUser entirely Absolute override — ignores all other settings Debugging only — breaks most assumptions
merge rules: scalar properties vs lifecycle hooks The merge of devcontainer.json + feature metadata uses different strategies per property type. For scalar properties like remoteUser, containerUser, and per-key entries in containerEnv: last value wins, with devcontainer.json having the highest priority. A feature cannot override the remoteUser you set — yours always wins, and all hooks (including hooks contributed by features) run as that one resolved user.

For lifecycle hook commands (onCreateCommand, updateContentCommand, postCreateCommand, postStartCommand, postAttachCommand): contributions are collected into an ordered list — feature commands run before devcontainer.json commands. Neither overwrites the other; both run, all as the same merged remoteUser.

For arrays like mounts, capAdd, securityOpt: contributions are unioned without duplicates.
